# AI作業・AI支援開発の運用標準 v1.3 — 第5章　作業工程

本ファイルは規範本文の一部である。章・節番号は旧統合版と同じ。文書全体の構成は[入口](../01-ai_work_operating_standard_v1_3_2026-10.md)に示す。

## 5. 標準開発工程

### 5.0 作業入口の選択

作業開始時に、目的に合う入口を一つ選ぶ。全案件を新機能のフル工程へ通さない。

| 入口 | 最小の進め方 | 実装へ進む条件 |
|---|---|---|
| 新機能・変更 | G0 → G1 → G2 → 必要ならG3 → G4 → G5 → G6 → G7 → G8 | 目的、受入条件、実現性、実装計画がそろい、実装・検証の記録を受入へ渡せる。 |
| 不具合・失敗の修正 | G0 → G1で再現・原因仮説 → 最小修正計画 → G6 → G7 → G8 | 元の症状又は失敗条件を再確認でき、修正後に同じ条件で検証できる。再現不能なら観測を増やすか`NOT EVALUABLE`にする。 |
| 構想・実現性の評価 | G0 → G1 → G3 → 「進める・明確化する・止める」の判断 | 採用手法の小さなE2E又は不可能性の証拠がある。実装は別の作業カードで開始する。 |
| 運用上の限定操作 | G0 → 現状・権限確認 → 最小操作 → 読み戻し | 権限、停止、復旧、受信側の確認が定義される。 |
| 文案作成・文書レビュー | G0 → 必要な入力・対象版の確認 → 文案作成又はレビュー → 元条件との照合 → 受入・提示 | 文書作業の範囲・条件・証拠が定まり、AI作業には第6.13節を適用する。製品実装・実稼働確認又は外部送達を含む場合は該当する入口・境界の確認を追加し、文書完成で代替しない。 |

軽量開発では、この入口と第9.1節の8項目を一枚にまとめてよい。入口を変える事実が判明したら、計画を更新してから実装又は再実行する。

### G0 受付・入力完全性

目的: 依頼と入力の欠落を、目的とリスクに照らして判定する。

実施:

- 依頼、添付、URL、対象リポジトリ、作業枝、コミット、環境、期限のうち今回の判断に関係する入力を、既存の作業カード又は入力一覧に記録する。
- 取得不能、切断、古い情報、矛盾を列挙し、判断を変え得るものは依頼者に確認する。質問、回答、未確定事項を記録する。
- 外部効果を伴う依頼かを判定する。
- 既存の承認と禁止がある場合は引き継ぐ。
- 第3.1節の条件で適用水準を選ぶ。軽量開発なら第9.1節の軽量作業カードに決定・受入責任者と統治不要の根拠を記録する。
- 統治が必要な場合だけ、組織図、役割表、任命書、契約・発注条件その他の根拠から、プロジェクト統治表を作る。組織図だけの場合は、決定権、委任、代理、工程別レビューを確認事項として残す。
- 統治が必要な場合だけ、第3.4節に基づき、工程ごとの段階レビュー、潜在的な参加役割、決定期限、エスカレーション先をレビュー計画にする。
- 安全で可逆な読み取り調査は、未確定事項を明示して進めてよい。変更、外部効果、受入判断は、必要な確認又は承認なしに進めない。
- 確認は、受入条件、リスク、次の判断に必要な範囲で終える。「確認のための確認」をしない。
- 作業規模に対して理解又は検証能力が不足する場合は、より適した主体、独立レビュー、又は作業分割を提案する。追加費用は承認なしに発生させない。

成果物: 軽量開発は軽量作業カード。通常又は高リスクは入力一覧、必要なプロジェクト統治表、必要なレビュー計画。

出口条件:

- 必要入力が揃う。
- 軽量開発では決定・受入責任者と統治不要の根拠が記録される。通常又は高リスクでは決定権者、受入責任者、必要な段階レビューが特定される。未特定なら、実行できる範囲を読み取り調査へ限定する。
- 欠落していても、調査だけを安全に進められる範囲が明確。
- それ以外は `INPUT_BLOCKED`（入力待ち）とする。

### G1 現状調査

目的: 文書上の想定と実状態を分ける。

内部調査では、今回の判断又は変更に関係する項目を、次から選んで確認する:

- Gitの状態、`HEAD`、作業枝、遠隔履歴、未コミット変更。
- 稼働中の処理、通信ポート、版、起動コマンド、作業ディレクトリ。
- 実効設定、形式定義、優先順位、環境変数、文字コード。
- 実行時状態、待ち行列、未完了作業、最後の終了イベント。
- データ、成果物、ハッシュ値、保存場所、保持期間。
- 現在のテスト基準、既知障害、直近の失敗分類。
- 主体、OS利用者ID、隔離実行環境、資格情報の所有者。
- リポジトリ、Git管理情報、状態保存先、一時領域、子プロセスの権限。
- 想定と差異があれば記録し、計画修正、権限要求、障害報告、又は中止のいずれかを選ぶ。現状調査だけを理由に改善作業を開始しない。

成果物: 現状記録、主体・資源対応表

出口条件: 実行経路と変更対象に残る未確認事項、その影響、確認又は判断の担当が分かる。変更の可否を左右する未確認事項を、確認済みとして扱わない。

### G2 目的・要求定義

目的: 何を解決し、何をしないかを固定する。

実施:

- 業務目的、利用者、成功指標を定める。
- 要求の主体と対象を明記し、別の対象や目的に読み替えられないようにする。
- 同じ対象には同じ用語を使う。
- 新たに定める要求は、確定前に内容と判断権限を依頼者へ確認する。依頼文や既存の承認で確定済みの要求について、同じ承認を求め直さない。
- 目的、非目的、受入条件、受入責任者を定める。
- 統治が必要な場合だけ、要求ごとに、業務・経理・システム・案件のどの役割が確認し、誰が裁定するかをレビュー計画へ対応付ける。
- 機能要求と非機能要求を分ける。
- 安全、信頼性、費用、性能、運用性、保守性、検証可能性のうち、対象の判断に関係する条件を確認する。
- 上記の優先順位と、適用区分（第3.6節）を明確にする。小規模・QuickWinへ、必要性の根拠なく大規模開発用の運用・検証を課さない。
- 既存仕様、会話、外部資料の援用条件を記録する。

成果物: 要求定義

出口条件: 受入条件が観測可能で、非目的と優先順位が明確。

### G3 外部調査・実現性

目的: 候補手法を選定し、現在の条件で実行できるかを確認する。代替案は、重要度、不確実性、費用に応じて用意する。

外部調査では、候補手法の採否に影響する項目を、次から選んで確認する:

- 公式機能、制限、認証、隔離実行環境、非対話動作、外部プログラムを調査する。
- OS、実行環境、SDKの互換性を調査する。
- イベント、通知、定期照会、順序保証、再試行を検証する。
- 価格、トークン、クレジット、計算資源、保存容量、通信費を確認する。
- セキュリティ、データ送信、保持期間、契約を確認する。
- 既知の失敗類型、公式の障害情報、再現手順付きの障害情報を確認する。
- 代替手法と撤退条件を定める。代替が必要な場合は、主候補、同じ要求を満たし得る代替候補、安全停止又は人間判断への切替条件を記録する。代替候補には、再利用する根拠、未確認事項、最小追加検証を対応付ける。
- 主体、非同期イベント、権限境界、復旧の関係を文章だけでは追えない場合は、タイミング図、フロー図、主体図のいずれかで経路を確認する。
- 検証が収束しないときは、論点、確認済み事実、選択肢、必要な判断を既存の記録にまとめる。技術的な指摘はレビュー担当に求め、権限や方針の判断は決定権者へ渡す。細部を無制限に調べない。

候補比較用の簡易構成:

- 候補手法を比較する必要がある場合は、対象機能の最小構成を役割名で記録する。個人名、製品名又はプログラム名は、役割を実現する候補手段として別に対応付ける。
- 最小構成には、主体、開始契機、主要な入力・出力、外部境界、信頼境界、主要な停止又は復旧の入口を含める。状態遷移、全データ構造、全例外経路を固定する基本設計はG4で行う。
- 候補手法で、元の依頼と確定した要求のどの結果を実現するか確認する。G2の要求一覧だけを見て、元の依頼に含まれる結果や失敗時の扱いを落とさない。G4で設計する機能、主要な入出力、停止又は復旧の入口を引き継ぐ。

方法候補ごとに確認:

- 現在の版と確認時刻。
- 直接根拠、推論、未確認。
- 選定基準、各基準の優先順位、数値化する場合の重み付け根拠、候補ごとの比較結果、採否理由。基準は、要求適合、安全・権限、実環境互換、費用、運用性、証拠追跡性、復旧性、既存資産の再利用性から、対象に必要なものだけを選ぶ。
- 実際の主体による読取・書込・実行の確認。
- 最小正常E2Eと最重要異常E2E。
- 自動修正又は人間判断が候補の動作に含まれる場合は、修正の許可条件、決定的な再検証、修正を止める条件及び人間判断に渡す証拠・選択肢を確認する。
- 費用上限と後始末。
- 合格、実行不能、却下のいずれかの判定。

成果物: G4引継ぎ欄を含む手法記録、費用記録、実行可能性の証拠

G4への引継ぎ欄には、採用候補、採用条件、未確認事項、代替手法、撤退条件、最小E2Eの結果及び残る実現性リスクを記録する。実現性、費用、権限又は外部条件を左右する未確認事項は、G4で暗黙に確定せず、G3へ戻すか人間判断へ上げる。

出口条件: 採用手法が実際の主体で小さく動く、又は不可能性が確定。

### G4 基本設計・制御設計

目的: 採用した手法について、今回の受入と安全に関わる経路を実装前に定義する。代替手法には発動条件と最小の検証方法を定める。

実施:

- 構成要素、主体、データ流れ、信頼境界を定義する。
- 機械的な処理とAI判断を分離する。
- 状態、イベント、制御条件、終了状態を定義する。
- 元の依頼と確定した要求を、設計する機能と主要な入出力に対応付ける。機能ごとの記載だけで終えず、機能間で何を受け渡すかを確認する。
- 設計対象の全経路を確認する。開始から受入又は停止まで、正常時、失敗時、復旧時、再実行時及び判断待ちからの遷移をたどる。各分岐の条件、渡す情報、遷移先、終了状態を確認し、途切れや重複、未定義の遷移を残さない。
- ここでいう全経路は、設計対象に含まれる分岐と状態遷移の種類を指す。入力値の全組合せや、設計範囲外の機能まで列挙する意味ではない。全経路の確認と、個々の経路を実行して検証することも区別する。実行検証の対象は、受入条件とリスクに応じて定める。
- 分岐、状態遷移、復旧又は複数主体間の受け渡しがある設計では、全経路を原則として図示する。図示を妨げる重大かつ具体的な事情がある場合は、別の方法で全経路を確認し、その事情と確認方法を既存の設計レビュー記録に残す。作図ツールは指定しない。
- リスク基準で選んだ正常系・異常系について、検知、停止、復旧、通知までの動作を確認し、対象範囲・除外理由・打切り条件をG4成果物へ記録する。
- 権限拒否、時間超過、空の出力、古い規則、重複イベント、終了コード0かつ成果物なしを、該当する場合に含める。
- 人への判断依頼に必要な情報、判断後の同一対象への再開先、再検査条件を定義する。判断後は、影響する権限、基線、費用、試行、証拠を再確認し、別の対象を自動選択しない。
- 長時間実行では、生存確認、定期状態通知、期限、ウォッチドッグの要否を定義する。
- 前工程で作成した図があれば利用する。ただし、その図に元の要求が欠けていないかを確認する。
- 証拠対応表を作る。

成果物: 構成文書、実行仕様、E2E確認記録、証拠対応表

出口条件: 元の依頼と確定した要求のうち、今回の設計対象に含まれる結果が機能と経路に対応している。設計対象の経路に未定義の受け渡しや遷移がなく、失敗時には復旧先又は終了状態が定まっている。

### G5 実装計画

目的: 設計を過不足のない作業単位へ落とす。

計画の順序とカードの選定は第6.14節に従い、承認された到達点の必要な前提と直後の受入確認へ接続する。

順序: 要求仕様 → 実装計画 → 作業カード。軽量開発では第9.1節の8項目を作業カードとし、以下の詳細項目は該当する追加確認モジュールがある場合だけ補う。

第9.1節の8項目に統合する詳細（当該作業又は第9.2節の該当モジュールで必要なものだけ）:

- 作業ID、担当主体、入力の版・ハッシュ値。
- 目的。
- 対象のパス、API、データ。
- 非目的。
- 前提条件。
- 許可操作と最大回数。
- 禁止操作。
- 費用上限。
- 期待結果と受領記録。
- 検証方法。
- 停止・判断依頼条件。
- 後始末。
- 次の状態。

粒度規則:

- 設計変更、実装、権限修復、データ移行を一枚に混ぜない。
- 一つの作業カードで一つの責務境界を変更する。
- 一つの作業カードで新しい基盤、画面、エージェントを同時に導入しない。
- 全体取得、一時退避、履歴の巻戻し、広い再構成は、局所操作で達成不能な証拠がある場合だけ計画する。

成果物: 実装計画、作業カード、テスト計画

出口条件: 各作業カードが単独で実施、検証、停止でき、前提・必要レビュー・許可を満たした後の次の状態が分かる。記述方法は第9.4節に従い、項目の列記だけで行動関係を実行者へ委ねない。AIが作成する指示は第6.13節P1～P4の照合を終え、必要な着手許可を得てから確定する。

### G6 実装

目的: 許可範囲内で最小変更を行う。

開始手順:

1. 最新の人間による指示を読む。
2. 権限一覧で正本の版を確認する。
3. 現在のカード又は指示要約を原文と照合する。確認済みで版・前提が不変なら再生成せず参照する。
4. 現状を再確認する。
5. 事前確認を実施する。
6. AI作業の計画クロスレビューと必要な許可・前提を満たした、現在選択した作業カード一件を開始する。これは同時着手の制限であり、一件終了ごとの人間への再承認要求ではない。

実行中:

- 意図、試行、結果を記録する。
- 対象範囲の機械的制御を適用する。
- 新しい不確実性は `UNKNOWN` として記録する。
- 新しい権限、費用、破壊操作が必要なら停止。
- 通常の内部失敗は、観測事実と原因仮説を分けて分類する。同じ失敗分類については、各修正の根拠を証拠で更新できる場合に限り、許可内で二回まで修正する。新たな権限、費用又は設計判断が必要になった時点、又は二回目の修正後も同じ失敗が再発するか受入条件を満たす証拠が得られないときは、三回目の小修正を追加せず、G4又は人間判断へ戻す。
- `STOP` を受けたら新規操作を開始しない。
- 原則を守り、不要な回り道をしない。
- 原則への適合、根拠、証拠が不足し、操作の可否を決められないときは、未確認事項を既存の記録に残す。レビュー担当には適合の確認を求め、権限や方針の判断は決定権者へ渡す。

カード終了後の扱い:

- 結果と証拠を記録し、AI作業では第6.13節E1～E4のクロスレビュー、その他の必要レビュー又は受入条件を満たしてから依存する後続へ渡す。
- 同じ依頼の後続カードまで許可され、前提証拠、必要レビュー、権限、累積上限を満たし、第6.14節による次作業の選定が妥当なら、必要な前提を解消するカード又は先に可能な受入確認へ進む。カード変更又は再開だけで時間・費用・試行の上限をリセットしない。
- 許可が現在カードまでの場合、必要レビューが未了の場合、又は範囲・権限・費用等の境界に達した場合は、その境界で止める。上位目的への寄与を後続着手の許可にしない。

成果物: 差分、試行記録、成果物

出口条件: 期待成果が生成され、検証へ渡せる。

### G7 検証

目的: 実装が要求を満たすかを確認し、試験条件や判定器の変更による見かけ上の合格を防ぐ。

本節は通常又は高リスクの作業に適用する。軽量・QuickWinでは、第9.1節で定めた受入条件に対応する検証を実施し、自己確認であることを記録する。AI作業の結果クロスレビューは第6.13節に従い、M6を選択した場合は追加の独立検証を適用する。自己確認をその代替にしない。

最小試験は、今回の変更、受入条件、具体的なリスクに関係する項目を次から選ぶ。変更していない外部境界や存在しないUIの確認は追加しない:

1. 変更受入条件の焦点テスト。
2. 関連する既存回帰テスト。
3. 変更した外部境界の小さな実E2E。
4. 最重要の失敗注入テスト。
5. 成果物、状態、遠隔状態、UIの独立した読み戻し。
6. テスト完全性の確認。

テスト完全性:

- 基準状態との差分を確認する。
- 除外、単独実行、期待失敗、期待値緩和を確認する。
- 模擬と実環境を区別する。
- 固定入力が本番用の生成経路と同じ経路を通るか確認する。
- 受入基準と独立確認用の判定器が事前に固定され、実装担当による変更で合格基準が緩められていないか確認する。試験の初期作成と、固定後の変更を区別する。
- 判定器、特定事例の固定化、評価対象への答えの漏洩を確認する。
- 出力、トークン、実行時間、切断、失敗を保持する。
- 条件不一致は `NOT EVALUABLE` とする。

テスト範囲停止規則:

- 各テストを受入条件又は具体的回帰リスクへ紐付ける。
- 紐付かないテストは追加しない。
- 実E2E通過後は、未達の受入条件又は新しい実在リスクがない限り追加しない。
- 数を品質指標にしない。
- 受入条件、具体的リスク、影響度に寄与しない検証へ時間や資源を使わない。

成果物: テスト証拠、完全性確認、E2E証拠

出口条件: 今回の元の受入条件に必要な検証が証拠で確認でき、AI作業の結果クロスレビューと適用する独立検証を通過する。機械的検査の合格だけで意味を含む条件の充足としない。未達・未評価を残す場合は完了とせず、継続又は判断対象を明示する。

### G8 受入・送達

目的: 実行、送達、適用、受入を混同せず閉じる。

実施:

- 受入条件ごとに証拠を照合する。
- 実装担当の自己申告と実状態を比較する。
- 送達が今回の作業に含まれる場合は、指定された受信者へ報告又は成果物を送る。
- 送達した場合は、受信者の受領記録を確認する。
- 適用が受入条件に含まれる場合は、適用状態を確認する。
- Gitで送達した場合は、コミットSHAと遠隔`HEAD`を照合する。
- UI要件は実際のUI操作を確認する。
- 未検証、残課題、復旧方法を提示する。
- 第6.13節の結果クロスレビューを確認し、今回の依頼の元条件へ最終照合したうえで受入責任者が判定する。局所成果物の完成を依頼全体又は製品全体の達成に拡張しない。

成果物: 完了報告、受入記録

出口条件: 受入責任者の判定、受入条件に対応する証拠、未検証・残課題・復旧方法が記録される。軽量・QuickWinの自己受入は自己確認であることを記録し、独立受入とは表示しない。外部操作の効果を受入対象に含める場合は、第1.5節の状態コードに従い、`VERIFIED`、又は明示的な `BLOCKED`（実行不能）、`REJECTED`（却下）、`NOT EVALUABLE`を記録する。

### G9 運用・学習

目的: 再発を減らし、測定自体を目的化しない。

実施:

- 生存状態、費用、失敗分類、復旧時間を記録する。
- 同一失敗の再発を監視する。
- 重要な実行境界と決定だけを履歴へ残す。
- ルール追加前に既存規則との重複・矛盾を確認。
- 機械的に判定できる規則は実行経路の制御へ移し、意図的違反試験で確認する。
- 不要になった規則、古い操作手順書、置換済み文書を整理する。

成果物: 障害・設計判断記録、規則有効性記録、保留一覧

出口条件: 再発防止がD3以上、又は未実装として責任者と期限が明確。
