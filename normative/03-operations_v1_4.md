# AI作業・AI支援開発の運用標準 v1.4 — 第6.1～6.12節　実施手順

本ファイルは規範本文の一部である。章・節番号は旧統合版と同じ。文書全体の構成は[入口](../01-ai_work_operating_standard_v1_4_2026-10.md)に示す。

## 6. 標準手順

### 6.1 指示受領

1. 入力が今回の判断に足りるか確認する。
2. 案件で定めた優先順位に従い、現在の指示と正本を特定する。
3. 指示から目的、対象、禁止、証拠、停止条件を取り出す。
4. 代名詞が指す対象や変更範囲に曖昧さがないか確認する。
5. 判断や安全に影響する曖昧さを、依頼者へ確認する。
6. 指示要約と原文を突合する。
7. `READY`（準備済）又は`INPUT_BLOCKED`（入力待ち）へ遷移する。

指示文の冒頭に「全文を読め」と書くだけでは不十分である。指示要約の各項目が、原指示のどこに由来するかを確認する。

### 6.2 現状確認

今回の変更や判断に関係する現状を読み取りで確認する。次のうち、対象に関係しない項目まで調査する必要はない。確認した事実と未確認事項は、既存の作業記録に残す。

- 現在の版、作業枝、`HEAD`、未確定変更。
- 実行中の処理、通信ポート、起動コマンド、作業ディレクトリ。
- 実効設定と読込元。
- 永続化された状態と未完了作業。
- 最後に確認できた外部受領記録。
- 直近の失敗、未完了、手動操作。
- 対象主体の利用者IDと隔離実行環境。
- 変更対象と依存先。

古い会話、予定、文書だけから現在状態を推定しない。

### 6.3 アクセス制御・隔離実行環境の事前確認

権限、資格情報、機密・個人・本番データ、又は隔離実行環境の境界を扱う場合に適用する（第9.2節のM2）。関係する操作について、次の対応を既存記録に残す。別の帳票を作る必要はない。

| 主体 | 利用者ID | 隔離実行環境 | 資源 | 読取 | 書込 | 実行・作成 | 確認結果 |
|---|---|---|---|---|---|---|---|

対象となり得る資源（今回触れるものだけを確認する）:

- 作業領域。
- `.git`と`index.lock`。
- エージェントの状態データベース。
- 一時領域。
- 子プロセス。
- 通信先。
- 資格情報の保存先。
- 成果物ディレクトリ。
- 外部API。

順序:

1. 読み取りだけの確認。
2. 隔離領域で対象を限った書込確認。
3. 拒否される境界の確認。
4. 本番と同じ主体による最小動作確認。
5. 必要時だけ限定したアクセス制御修正を承認。
6. 修正後に同じ確認を再実行。

通常の利用者が書き込めても、隔離実行環境の利用者IDが書き込めるとは限らない。策定時の事例は[参考付録B・E09](../support/APPENDICES_v1_4_2026-10.md)を参照する。

### 6.4 正常系ウォークスルー

実行経路又は外部効果を変更・評価する場合は、今回の受入条件に関係する段階を開始から結果まで確認する。送達や適用がない作業に、その段階を追加しない。

| 段階 | 確認 |
|---|---|
| 開始契機 | 誰が何を契機に開始するか |
| 受領 | 入力を受け取った証拠 |
| 開始 | 実行中の処理又は作業が開始した証拠 |
| 操作 | 対象主体が許可範囲で操作 |
| 成果物 | 期待成果の存在と内容 |
| 送達 | 受信者が受領 |
| 適用 | 後続が処理 |
| 独立確認 | 独立した読み戻し |
| 受入 | 受入責任者が受入条件を判定 |
| 終了処理 | 処理、費用、一時領域の後始末 |

### 6.5 異常系ウォークスルー

実行経路又は外部効果を変更・評価する場合は、次のうち今回の経路で影響が大きい失敗を選ぶ。全項目の試験を一律には求めない。

- 入力欠落又は切断。
- 古い規則又は古い作業枝。
- 権限拒否。
- 資格情報不足。
- 子プロセス未起動。
- 時間超過又は孤児化。
- 終了コード0かつ成果物なし。
- 送信済みだが受信者未確認。
- 重複イベント。
- 空の出力又は切断。
- 模擬環境だけで成功。
- テスト改変による見せかけの合格。
- 状態は実行中だが進捗なし。
- 人間の承認後に再開先なし。

各異常に、検知方法、状態、再試行可否、責任者、証拠、復旧、終了状態を定義する。

### 6.6 長時間実行エージェント

必須項目:

- 実行回ID、作業ID、試行ID。
- 開始時刻、期限、最大無音時間。
- 定期状態通知に、現在操作、最後の永続化済み確認点、次に予期するイベントを含める。
- イベント源と定期照会による代替経路。
- 未解決の停止要求は一件だけ。
- 重複防止キー。
- 再試行上限。
- 孤児化検知。
- 永続化された再開地点。
- 終了証拠。

判定:

- プロセス生存は生存状態の証拠に過ぎない。
- 定期状態通知の更新は活動中の証拠に過ぎない。
- 永続化済み確認点が増えなければ進捗ではない。
- 期限超過時は同じ操作を無限に再試行せず、分類して停止又は復旧する。

### 6.7 Git操作

- 開始時に作業枝、`HEAD`、状態、遠隔履歴を記録する。
- 関係のない未確定変更を消さない。
- 許可ファイルを固定する。
- 追加登録の前後で対象ファイル名だけの一覧を確認する。
- コミット後にローカル`HEAD`を確認する。
- 送信後に遠隔`HEAD`を照合する。
- 取得が目的でない場合、必要ファイルだけを取得する。
- 一時退避、履歴巻戻し、掃除、強制操作、作業枝全体の取得は別承認対象とする。
- Git操作が可能な主体を事前確認で決める。
- 実行環境操作担当を使う場合、起動経路と候補の受領をE2Eで確認する。

### 6.8 外部送達

- 送信前に宛先、権限、重複防止IDを確認する。
- `SENT`と`RECEIVED`を分ける。
- UI表示やローカル送信箱の保存を受信と呼ばない。
- 文面一致から受信を推定しない。
- 送信結果不明時は自動再送せず、重複防止又は状態照会で判定する。
- イベントを生成しても、受信側の処理が起動するか確認する。
- 受動的な置き場には、監視者又は人間による中継を明示する。
- 報告IDの不一致は無視せず、拒否理由を返せる手順にする。

### 6.9 人へのエスカレーション

人間へ判断を求めるときは、既存の作業記録に次の情報をまとめる。原則24の「判断依頼書」は、この情報を一つの判断依頼として参照できる記録を指す。専用の帳票を増やす必要はない。

- 決めること。
- なぜ自動決定できないか。
- 確認済み事実。
- 選択肢と影響。
- 推奨案と理由。
- 費用、危険、可逆性。
- 承認後の再開状態。
- 判断期限。

同じ承認を再要求しない。細かな障害を一件ずつ送らず、内部で解決できないものをまとめる。

### 6.10 停止、訂正、撤回

`STOP`受信時:

1. 新規操作を開始しない。
2. キュー済み操作を停止可能なら停止。
3. 実行中で中断が危険なら、安全な最短確認点だけ作る。
4. `STOP`後に発生した操作を全て報告する。
5. 再開は新しい明示指示後だけ。

誤った主張を訂正する時:

1. 誤った主張を特定する。
2. 正しい状態を`OBSERVED`又は`UNKNOWN`で記録する。
3. 誤りに依存した判断を列挙。
4. 影響した成果物を未検証へ戻す。
5. 必要な再検証を定義する。
6. 根本原因がUI誤読、対象誤解、古い状態、証拠不足のどれか分類。

### 6.11 二回の小修正後の設計復帰

同一の失敗分類が二回再発したら:

- 新しい小修正を止める。
- 元の目的と現状を再提示する。
- 呼出経路と状態遷移を端から歩く。
- 権限、開始契機、主体、アクセス制御、受領記録を再確認する。
- 部品はあるが配線がない箇所を探す。
- 現設計で達成可能か判断。
- 修理、迂回、縮小、廃止から選ぶ。
- 設計判断記録を残す。

「細かい修正が続く」は実装者の怠慢と断定せず、設計、前提、観測、受入のどこが欠けたかを調べる。

### 6.12 段階レビューと承認

組織上の段階レビューは、通常又は高リスクで統治が必要な場合に適用する。第3.4節の役割例から必要な参加者を選び、プロジェクト統治表で確定した決定権者が主宰又は委任する。

- AI作業のクロスレビューは適用区分にかかわらず第6.13節に従う。確認の統合・再利用は第6.14節に従う。
- 軽量開発では会議を開かず、第9.1節の軽量作業カードに決定・受入と証拠を残せばよい。
- 会議を開いたこと、資料を送ったこと、出席者が異議を述べなかったことは、承認又は受入にならない。

レビュー開始前に、次を配付又は参照可能にする。

- 対象成果物、その版、対象範囲、前回からの差分。
- 当該工程の受入条件、未解決事項、前提、依存、リスク、選択肢。
- レビュー参加者の役割と、今回の確認・承認・裁定の権限。
- 期待する決定と、決められない場合のエスカレーション先・期限。

レビュー記録の必須項目:

- 工程、対象、版、日時、参加役割、欠席した必須役割。
- 確認した事項、指摘、対応責任者、期限、未解決事項。
- 決定結果（継続、条件付き承認、差戻し、保留、却下）、決定権者、条件、有効範囲。
- 次工程へ進める条件、再レビューの要否、エスカレーション先。

条件付き承認は、条件、責任者、期限、未達時の状態を記録し、条件の確認なしに最終受入又は稼働開始へ進めない。要求、予算、契約、設計、運用、受入の変更は、影響する役割の再レビュー対象とする。
