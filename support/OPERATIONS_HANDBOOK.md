# 運用ハンドブック v0.6

改訂履歴: 2026-09-26 初版／v0.2 条件別選択・再生成と検証手順を追加／v0.3 質問の平易化と候補一覧の保存を追加／v0.5 公開版として整理／v0.6 工程横断の実装・検証・証拠・配送・リポジトリ整理TIPSを追加

対象: 運用標準とテンプレート集を採用・改版・点検する人

## 1. 目的と非目的

このハンドブックは、標準を既存の案件運営へ過不足なく取り込むための補助である。文書を増やすこと、全テンプレートを埋めること、AIに採否を決めさせることを目的にしない。

案件ごとの目的、許可、責任、受入は、運用標準と案件の正本に従う。この文書は承認権限、法的判断、リスク受容、費用上限を与えない。

## 2. 導入の最小経路

| 段階 | 行うこと | 残すもの |
|---|---|---|
| 読む | 運用標準の目的・状態・比例適用と、案件の正本を確認する。 | 参照した版と未確認事項 |
| 統合する | 既存の作業カード又は帳票へ、必要なC1〜C8と固有の問いを統合する。 | 統合先と選択理由 |
| 実施する | 許可済みの範囲でのみ、工程・検証・受入を進める。 | 既存の実行・検証・受入記録 |
| 振り返る | 手戻り、引継ぎ、証跡、追加負担を観察する。 | 効果評価計画に沿う観察記録 |

軽量利用では、テンプレートを独立ファイルとして増やす必要はない。[テンプレート集の軽量利用例](../templates/README.md)と運用標準3.6・9.1を参照し、既存の一枚の作業カードへ必要な問いを統合する。

## 3. テンプレートを選ぶとき

1. まず、案件の目的・対象外・受入・責任者・許可を確認する。
2. 次に、既存帳票で足りない問いだけを特定する。
3. [カタログ](template-catalog.json)又は[選択補助](template-selector.html)で候補を探す。PJのGiven Conditionsを回答し、Loose／Medium／Tightで確認の厚みを比較する。
4. テンプレート本文の「使う場面・統合先」と、一覧の参考トリガーを読む。
5. 採用する問いと統合先、判断に影響する未確認事項を案件記録へ残す。未採用の全テンプレートの理由を記入する必要はない。

候補表示は、適用の命令ではない。参考トリガーに当てはまっても、追加調査、権限変更、外部送達、費用発生を許可しない。

### 条件と厚みを分けて考える

Given Conditionsは作業内容、決定主体、費用、前提、利用者、変更、構成、データ、個人・機密情報、品質影響、攻撃・権限境界、提供、運用、AI用途、AIへの委任、モデルの扱いの16問で把握する。各問は具体的な3段階と未確認を持つ。回答は対象案件の条件であり、案件規模や規範上の適用区分の認定ではない。

| 厚み | 記録・確認の目安 | 条件との関係 |
|---|---|---|
| Loose | 直接必要な判断と根拠を、既存カードの短い欄へ統合する。 | 個人情報、契約、連携、自律操作等の直接条件があれば対応する問いを含む。 |
| Medium | 計画・設計・検証の対応と担当間の引継ぎを追えるようにする。 | 該当領域の補助的な問いが加わる。 |
| Tight | 前提・代替案・影響・見直し条件まで詳しく照合する。 | 該当領域をさらに掘り下げる。AIを使わなければモデルカードは候補にならない。 |

厚みを変えても、標準の必須事項、受入責任、独立性、権限は変わらない。目的・範囲・問題の共通の問いは全段階で候補になり、他は条件と厚みによって選ばれる。候補数は独立文書数ではない。

画面では同じ回答で3段階の候補数を比較し、各票に「今回の位置付け」「使う判断」「統合先」「参考トリガー」「入力と出力」を表示する。強い条件が多数あれば、Looseでも多くの観点が必要になる。件数を減らすために回答や厚みを変更しない。

### 候補外と未確認の読み方

- **候補**：回答と厚みから選択条件に該当したもの。採用は案件側が判断する。
- **確認を厚くすると候補**：関係する条件は確認できているが、現在より厚い確認で扱う補助観点。
- **条件未確認**：候補になり得る回答が未確認。必要性を確定せず、関係する質問を表示する。
- **現回答では候補外**：選択ルールの条件に該当しないもの。折りたたみを開くと役割と参考トリガーを確認できる。

全50件は上記のいずれかに現れる。未確認を「対象外」や「最大条件」とみなさない。AIなしを選ぶとAIの委任・モデルの質問は対象外となる。T43・T44・T48はデータ品質や攻撃耐性の問いとしてAIなしでも関係し得る。

画面の質問と選択肢は日常の作業を例にした表現へ改めている。例えば「既存資産・変更・提供順序」は「今ある仕事のやり方やシステムを変えますか？」、「未確認」は「まだ分からない」と表示する。質問のID、回答の段階、文書を選ぶ条件はv0.2から変えていない。画面の「回答待ち」「より詳しく確認すると追加」「今は含めない」は、それぞれ上記の未確認・厚みを上げると候補・候補外に対応する。

### 候補一覧をJSON／CSVへ保存する

結果の上にある保存ボタンを押すと、現在の回答と確認の詳しさから選ばれた候補一覧をファイルにできる。回答や厚みを変えた後の保存には、その時点の内容が反映される。

| 形式 | 内容と用途 |
|---|---|
| JSON | 回答のID・質問文・選択値・回答文・未確認／対象外の区別、候補文書の役割・理由・統合先・参照パス、ルール版と元資料のハッシュ。ほかのツールへ渡す際に使う。 |
| CSV | 1候補1行。ID・名称・役割・理由・統合先・参照パスに、選んだ厚み・未確認の質問数・全回答・日時・ツール版を添える。表計算ソフトで一覧を確認する際に使う。 |

出力対象は候補文書の一覧であり、採用・承認済みの宣言ではない。テンプレート本文や実案件の記入済み文書は添付しない。全50件カタログとは別のファイルである。JSONには4区分の件数も含めるが、候補外の文書本体は含めない。CSVは日本語用のUTF-8 BOM付き、カンマ区切り、CRLF改行で生成する。

ファイルの文書パスはリポジトリのルートからの相対パスであり、出力ファイルだけを別の場所に移してもリンク先の文書が添付されるわけではない。保存先やファイル名の最終処理はブラウザの設定による。外部通信・自動保存・保存済み回答の読み戻しは行わない。保存に成功したかは、ブラウザ側のダウンロード結果で確認する。

### ルールの位置付け

[selector-rules.json](selector-rules.json)の各条件は、テンプレート本文の参考トリガーを質問へ対応付けた編集上の目安であり、運用効果を検証済みの判定器ではない。各票に複数の条件を持たせ、いずれかを満たせば候補になる。一つの条件内の複数回答は全て必要である。条件にはLoose／Medium／Tightのどこから補助確認に含めるかを指定している。画面の理由から、どの回答で選ばれたか確認できる。

元の一覧の「軽量・中規模・大規模」の参考度は、カタログの`guidance`に保持するが、Loose／Medium／Tightへ変換しない。候補が実際の仕事と合わない場合は、その票の役割・トリガー・回答を照合し、案件の既存資料で補うかルールの改訂候補にする。

## 4. 改版時の確認

改版は、次の順で小さく確認する。

1. 変更対象、目的、非目的、正本との関係を記録する。
2. テンプレートのID、名称、相対リンク、表の列、一覧との対応を検査する。
3. 新旧で意味が変わる箇所は、運用標準を上書きしていないか、人間の受入や既存権限をAIの提案と混同していないかを確認する。
4. 検査の範囲、実行日時、結果、未検査事項を改訂記録へ残す。
5. 構造検査の成功だけで実務効果、法的適合、案件受入を主張しない。

継続的な検査を導入する場合も、まず上記の確認対象を版管理する。CIの採否は利用側の環境・費用・権限に従う。

### カタログとHTMLの再生成・検査

Node.jsを利用できる環境で、リポジトリのルートから次を実行する。追加パッケージや外部通信は不要。

```powershell
node support/build-selector.cjs
node support/build-selector.cjs --check
node support/verify-selector.cjs
git diff --check
```

生成処理は、テンプレート本文・一覧と選択ルールから`template-catalog.json`を作り、画面ソースと選択処理をまとめた`template-selector.html`を作る。この2ファイルは生成物として扱う。新規の編集は各Markdown、`selector-rules.json`、`selector-page.html`、`selector-engine.js`へ行う。

検査は、元文書との同期、全50IDの一意性、実ファイルへのリンク、全票が回答から候補になること、厚みを上げたときの単調性、AIなし・個人情報・未確認・複合条件の境界、3つの架空例を確認する。加えて、JSON／CSVの候補・回答・理由の一致、CSVの日本語・引用符・改行、保存ボタンの処理を画面部品の代替物で検査する。HTMLには同じカタログと選択処理を埋め込むため、別の手書き一覧とのずれを防げる。実ブラウザの描画・ダウンロード完了、実案件での適切さは別途確認する。

## 5. 参考文献を読むとき

[参考文献台帳](../templates/REFERENCES.md)の「種別」は資料の性格、「この集への利用範囲」は参照した観点を示す。外部資料はすべてテンプレート集の参考であり、このリポジトリの規範ではない。各資料の確認範囲・版・法域・未確認事項も併読する。

## 6. 停止と引継ぎ

判断権者が不明、権限や費用の追加が必要、証拠が不足、又は案件の指示と補助資料が矛盾する場合は、補助資料を根拠に補完しない。根拠・影響・対応案・判断先を既存の引継ぎ記録へ渡す。

## 7. 複数部品を一つの製品経路へ接続するとき

個別部品の試験が全て合格しても、部品間の識別子、永続化、呼出順序又はproduction compositionが未接続なら製品経路は成立しない。実装計画では、個別カードに加えて次の統合不変条件を既存の設計・試験計画へ統合する。

| 観点 | 確認例 |
|---|---|
| 同一性 | run、対象、criterion、契約版、設定fingerprint、権限decision、report・response・effectが必要な境界で一致する。 |
| 書込み前検査 | 欠落、部分一致、別対象又は古い入力を、状態変更より前に拒否する。 |
| currentとhistory | 履歴を現在状態へ混入させず、現在対象を履歴用入力で更新しない。 |
| 非同期終端 | workerの最終状態を保存した後だけ、一回の後続通知を行う。開始呼出しの戻りを完了にしない。 |
| 再適用 | 同じ結果は無書込み、競合結果は拒否。終端状態は単調である。 |
| 再起動 | 新しいプロセス又は構成の再生成後も同じ状態を読み戻せる。 |

統合試験は、実運用で使う構成起点、ハンドラ又はcomposition rootを通す。直接呼出しや注入fixtureしか通っていない場合は、その証拠水準を明記する。

## 8. 検証水準と試行記録

結果には「何が通ったか」だけでなく、どの水準まで証明したかを付ける。

| 水準 | 代表的な証拠 | それだけでは証明しないもの |
|---|---|---|
| 実装 | ガード又は処理の存在 | その分岐が実際に働くこと |
| assertion | 期待・拒否・非変更の明示検査 | 部品間の接続 |
| 部品fixture | 決定的な単体・部品試験 | production composition |
| 統合fixture | 実構成起点と決定的executor | 実サービス・実外部主体 |
| 実主体の過去証拠 | 固定された実行trace | 現在も稼働していること |
| 現在の製品E2E | 実UI・API・永続状態の同一run読戻し | 他環境・他対象・リリース受入 |
| 受入・リリース | 固定成果物、環境、責任者の判定 | 除外した条件又は全案件への一般化 |

試験記録では、テスト本体の不合格、収集失敗、ハーネス起動失敗、修正後の合格を分ける。追加試行を行う場合は、承認された対象コマンド、追加回数、時間・費用範囲、decision IDを残す。最終件数だけで途中の失敗を消さない。

発生時だけ評価できる修復、切断復旧、レビューなどは、発生しなければ`NOT EVALUABLE`とする。受入のために障害を人工的に発生させるかどうかは、危険・費用・必要性を別に判断する。

## 9. 要求・応答・後続効果を扱うとき

レビュー、承認、配送又は自動継続では、要求ID、応答ID、応答が参照する要求ID、後続効果IDを別々に保持する。保留応答の再利用前には、保存済み対象、応答本文の参照先、現在の未完了対象、応答の現存を再確認する。

一致しない応答は削除又は成功扱いにせず、次を記録して失効させる。

- 応答ID
- 期待した対象ID
- 実際の参照ID
- 不一致又は重複の理由
- 後続効果を起動していないこと

イベント通知、定期取得、応答処理、後続エージェント起動は別の生存領域である。一つが動いていることから他の稼働を推定しない。受信、適用中、適用済み、後続効果確認済みを分け、終了コード0だけで効果確認済みとしない。

## 10. 権限、上限、費用を実行へ結ぶとき

自動処理が権限を消費する場合は、権限記録を対象、効果、対象版又はcommit、設定fingerprint、回数・時間・費用上限、発行・失効時刻へ結び付ける。失効時刻以降は許可せず、不明な事実を許可へ補完しない。外部前提の観測と、人間が与えた許可は別記録にする。

ACTIVE_WORK、待機、transport作業、実行時間を分ける。費用上限0円は請求実測0円ではない。費用又はtokenを取得できなければ、理由付き`UNKNOWN`を保持する。

人間判断を求める場合は、一度に決める事項を一つにし、確認済み事実、選択肢、推奨、影響、許可範囲、再開地点を示す。チャット等で直接得た明確な判断は、原文、対象、効果、上限、経路、既知のID・時刻を記録し、別媒体で同じ承認を繰り返し要求しない。

## 11. 証拠パックと再現可能な成果物

証拠パックは、受入判断を変える情報に絞り、次を既存の試験結果又は受入記録へまとめる。

- 一意のパックID、対象commit、対象パス、受入条件
- 初回の失敗、修正、最終結果と各試行の権限
- raw artifactのbyte数、SHA-256、必要ならGit blob ID
- 原本、公開時の転送物、表示用転記の区別
- CRLF/LF、文字コード、圧縮等の変換
- バイト再現性を主張する場合のOS、生成ツール・ライブラリ版、完全なコマンド、設定・環境変数
- 観測できなかった事項と、その主張への影響

source commit又はファイル一覧の一致だけで、ZIP等のバイト列再現性を主張しない。人が転記したOS照会結果は、直接会話等の出所と限界を示し、native監査ログと呼ばない。

## 12. リポジトリを整理するとき

`未Pushをなくす`又は`作業ツリーをcleanにする`作業では、最初に未追跡物を次へ分類する。

1. 公開すべき製品ソース・文書
2. 機械固有の設定
3. 実行状態、ログ、証拠、SQLite等
4. 秘密・個人データ・チャットexport
5. 生成物、仮想環境、モデル、依存物
6. 保存が必要な未送信履歴

1だけを通常の公開候補とし、2〜5はlocal override又はignore等へ分離する。6を消す必要がある場合は、remote archive branch等の追跡可能な退避先へ保存し、遠隔読戻し後にだけローカル参照を整理する。`git clean`、hard reset、force push、一括追加を整理の近道にしない。

## 13. リリース記録を更新するとき

リリース記録は、計画時点の状態、現在状態、対象成果物を分ける。限定リリースでは、成果物ID・hash、環境、利用者、接続範囲、実行モード、費用・認証条件、除外事項を固定する。

以前の`NO_RELEASE`又は`未配布`を履歴として残す場合は、現在状態ではないことを明記する。リリース決定後も、実修復、current review、継続監視等の未評価事項を自動的に受入済みへ昇格させない。
